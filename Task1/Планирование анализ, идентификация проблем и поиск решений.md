## Cуществующие и потенциальные проблемные места
###  RabbitMQ как единая точка отказа (SPOF)

**Факты:**

* RabbitMQ используется для критически важной бизнес-интеграции (CRM ↔ MES).
* Нет указаний на:
  * кластеры,
  * подтверждения обработки (ack/nack),
  * DLQ,
  * идемпотентность сообщений.
* После открытия API поток сообщений резко вырос.

**Проблемы:**

* Потеря сообщений → заказы не переходят между статусами.
* Повторная доставка → дубликаты заказов или неконсистентные статусы.
* Очереди могут быть заблокированы «тяжёлыми» сообщениями.

**Вывод:**
RabbitMQ используется как “best effort”, тогда как фактически он — **шина транзакционного бизнеса**.

---

### 2.2 Асинхронная бизнес-логика без консистентной модели состояния

**Факты:**

* Статусы заказа меняются в 3 разных системах.
* Нет центрального “источника истины” по заказу.
* Нет механизма валидации переходов состояний.

**Проблемы:**

* Заказ может:
  * быть `PRICE_CALCULATED`, но не попасть в CRM;
  * быть взят оператором без подтверждения CRM;
  * зависнуть между статусами без автоматического восстановления.

**Вывод:**
Архитектура страдает от **eventual inconsistency без компенсирующих механизмов**.

### Архитектура и надёжность

1. **Укрепление RabbitMQ**

2. **Введение централизованной модели заказа**
   * Order Service / Order State Machine.
   * Явные правила переходов статусов.
   * Гарантированная доставка событий.
