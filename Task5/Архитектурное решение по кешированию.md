## «Мотивация».
### Мотивация к внедрению кеширования

#### Почему необходимо кеширование

Кеширование — эффективный механизм повышения производительности информационной системы. Его внедрение обосновано следующими ключевыми факторами:

1. **Рост нагрузки на систему.** С увеличением числа пользователей и объёма данных серверные ресурсы испытывают возрастающую нагрузку. Кеширование снижает количество прямых обращений к основным источникам данных (БД, внешним API, файловой системе).

2. **Задержки при получении данных.** Доступ к «холодным» данным (из базы, удалённого сервиса) требует времени на:
* установление соединения;
* выполнение запросов;
* передачу данных по сети;
* обработку на стороне сервера.

Кеш устраняет эти задержки, храня «горячие» данные в быстродоступной памяти.

3. **Оптимизация использования ресурсов.** Сокращение числа запросов к БД и внешним сервисам:
* снижает нагрузку на CPU и дисковую подсистему;
* уменьшает сетевой трафик;
* продлевает срок службы оборудования за счёт снижения интенсивности использования.

4. **Улучшение пользовательского опыта.** Быстрая загрузка страниц и мгновенный отклик интерфейса напрямую влияют на удовлетворённость пользователей и конверсию.

5. **Масштабируемость.** Кеширование позволяет системе выдерживать пиковые нагрузки без немедленного наращивания аппаратных ресурсов.

#### Проблемы, решаемые кешированием

* **Высокие времена отклика** — медленная загрузка данных из-за удалённости источников или сложности запросов.
* **Перегрузка базы данных** — массовые однотипные запросы к БД, вызывающие «просадки» производительности.
* **Зависимость от внешних сервисов** — задержки и ошибки при обращении к API третьих сторон.
* **Избыточные вычисления** — повторный расчёт одних и тех же данных (агрегации, трансформации).
* **Неэффективное использование пропускной способности сети** — многократная передача идентичных данных.


## «Предлагаемое решение»
- MES API -> MES db - Refresh-Ahead + Write-Through. 
 
RA - работает для обеспечения отображения свежих заказов, который можно вязть в работу. 
WT - обновляет кеш, помечая заказы как взятые в работу.

Почему не Cache-Aside. Низкая скорость обновления данных. Обрабатываются только операции чтения, а не записи. Следовательно, любая операция записи всегда будет миновать кеш и выполняться непосредственно в базу данных, что считается медленной операцией.
Несогласованность данных в кеше с базой данных. Запись делается в базу данных, но не в кеш — в нём всё ещё старые данные. Чтобы справиться с этим, разработчики обычно используют параметр TTL для содержимого кеша и продолжают отдавать потенциально устаревшие данные до истечения TTL.

- Internet Shop -> Shop API - Cache-Aside.
 
Храним стат данные на стороне клиента. 

Почему Cache-Aside - данные обновляются редко, допустима задержка в несколько секунд.

Почему не Write-Through - CRM часто меняет данные вручную, лишние синхронные операции.

- Shop API -> Shop DB - Read-Through. 

Храним данные о прочитаном заказае по TTL, чтобы предотвартить повторыне чтения из постоянного хранилища
Кеш не обновляется на стороне приложения — теперь это ответственность базы данных. В стратегии Read-Through кеш является вспомогательным сервисом БД и приложению не нужно обновлять кеш при чтении.

Почему не Cache-Aside. Низкая скорость обновления данных. Обрабатываются только операции чтения, а не записи. Следовательно, любая операция записи всегда будет миновать кеш и выполняться непосредственно в базу данных, что считается медленной операцией.
Несогласованность данных в кеше с базой данных. Запись делается в базу данных, но не в кеш — в нём всё ещё старые данные. Чтобы справиться с этим, разработчики обычно используют параметр TTL для содержимого кеша и продолжают отдавать потенциально устаревшие данные до истечения TTL.

- CRM -> CRM API - Cache-Aside. 

Статические данные о заказе. Уменьшаем кол-во данных передаваемых по сети.

Почему Cache-Aside - данные обновляются редко, допустима задержка в несколько секунд.

Почему не Write-Through - CRM часто меняет данные вручную, лишние синхронные операции.

- CRM API -> 3d files storage - Read-Through. 

Храним данные о прочитаном заказае по TTL, чтобы предотвартить повторыне чтения из постоянного хранилища
Почему не Cache-Aside - т.к. данные могу быть довольно объемны, хранить их на стороне клиента увеличивит наклодные расходы клиента

### стратегия инвалидации кеша
- MES API -> 3d files storage - Refresh-Ahead + Write-Through. Временна, устанавлениваем TTL времени жизни обхектов + "по ключу" для данных которые взяли в рабтоту
- Internet Shop -> Shop API - Cache-Aside. TTL других сопособ нет
- Shop API -> Shop DB - TTL
- CRM -> CRM API - Cache-Aside. TTL других сопособ нет
- CRM API -> 3d files storage - Read-Through. TTL.
